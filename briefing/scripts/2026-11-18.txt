Let's start with security, and specifically the vulnerabilities that should shape your patching plans today. There is a lot of Java in this one.

The biggest story this morning is a Java bug that researchers have already nicknamed Java Four Shell. The name is a deliberate nod to Log Four Shell, and while this is not the same scale yet, it deserves the same kind of attention from your teams.

Here is what happened. On Tuesday, the security firm Calif published details of a memory corruption flaw in the Java virtual machine, specifically in the fast Base sixty-four decoder that Java uses on Intel and AMD servers with the AVX five twelve instruction set. Base sixty-four is the encoding that turns binary data into plain text, and it is everywhere. Login tokens, API calls, file uploads. A malformed string with one extra padding character makes the decoder write past the end of its buffer. According to Calif, that can be turned into remote code execution without any login.

Calif says it demonstrated exactly that against default installations of Jira, Confluence, Jenkins and Keycloak. Those product-specific attack chains have not been published. Cisco Talos says the bug affects OpenJDK seventeen point zero point six and later. ARM servers are reportedly not affected.

Oracle and the OpenJDK project released fixed builds the same day, as part of Oracle's November Critical Security Patch Update. Oracle scores the flaw eight point one. Talos and Calif rate it nine point two on the newer scoring system. CISA, the US Cybersecurity and Infrastructure Security Agency, issued an alert urging immediate patching, and South Korea's intelligence service sent an urgent advisory to public institutions as well.

The good news: as of this morning, nobody has reported exploitation in the wild, and the bug is not in the known exploited list.

So what should you do? First, inventory. Java hides inside appliances, vendor software and container images, and often does not show up as its own line in your asset database. Second, patch internet-facing systems first. If you run Red Hat, Amazon Corretto, Azul or another distribution, watch for that vendor's build, because those may arrive a little later. Third, if you cannot patch right away, several security vendors recommend starting the Java virtual machine with the Base sixty-four hardware acceleration switched off. Talk to your application owners before you do that, because it can slow down some workloads, and on newer Java versions it may not fully close the hole according to Orca Security.

And finally, ask your key software suppliers, especially anyone running Atlassian or Jenkins on premises, when their bundled Java will be updated. This one is worth a short status check in today's operations meeting.

Second, a story that directly hits infrastructure teams. CISA, the US cyber agency, has added a flaw in Perforce Puppet Enterprise to its catalog of known exploited vulnerabilities. That means CISA has evidence of attacks in the wild. US federal agencies must fix it by the first of December.

Puppet, if you are not close to it, is the configuration management system many operations teams use to push settings and software to thousands of Linux and Windows servers. The Puppet Server is the brain. Whoever controls it can effectively control every machine it manages.

The bug sits in how Puppet Server processes the reports that agents send back after each run. Any client holding a valid agent certificate can send a specially crafted report and run code on the server. That alone is serious, because every managed machine has such a certificate. It gets worse if your certificate authority is set to sign new requests automatically. In that setup, an attacker with no credentials at all can simply request a certificate and then attack.

Vulnerability trackers rate it nine point four out of ten. Researchers at the security firm Neodyme found it, and reports say working exploit code is now public. The project's own advisory reportedly includes a sample malicious report that runs a shell command on the server. So the bar for attackers is low.

Perforce has fixed it in Puppet Enterprise twenty twenty-three point eight point thirteen, twenty twenty-five point twelve point one, and twenty twenty-six point zero point one. The open source fork OpenVox has fixed server releases too.

Notably, CISA now references a new directive called Binding Operational Directive twenty-six dash zero four, Prioritizing Security Updates Based on Risk. It pushes agencies to fix exploited flaws on internet-facing systems that give full control first. That is a sensible model for any organization.

What to do today: find out which Puppet version you run and patch it. Check whether certificate autosigning is enabled, and if it is, switch it off or require strong verification. Restrict who can reach the server's report interface. And review which agent certificates were signed recently, because an unexpected new certificate could be the first sign that someone got in.

Next, the Apache web server. Last week Apache released version two point four point seventy-one to fix a critical bug in its HTTP version two module. On Tuesday, Singapore's Cyber Security Agency said the flaw is reportedly being actively exploited, and that proof of concept code is public.

The bug is a race condition. In plain terms, two parts of the server handle the same piece of memory at the wrong moment, and an attacker can use that to run code without logging in. Every version from two point four point fifty-five to two point four point seventy is affected, but only where HTTP version two is turned on. The security company F five Labs rates it nine point eight. Singapore's agency uses a lower score of eight point one. Either way, it is serious.

One caveat. F five had reported no meaningful exploitation just one day earlier, so the picture is still developing.

What to do: update to the fixed version, or to your Linux distribution's patched package. Remember appliances, load balancers, and vendor products that ship their own copy of Apache, because those will need a vendor update rather than your normal Linux patching. If you cannot patch today, turning off HTTP version two on exposed servers removes the risk.

On to attacks and breaches. Two supply chain compromises lead today, one hitting websites you probably visited this week, and one hitting a Microsoft package that developers install every day.

The lead story here is a supply chain attack on the web itself. Optimizely is a widely used platform for website experiments, the kind of A B testing that marketing teams run on live pages. Customer sites load a small Optimizely script on every page view.

On Sunday, November sixteen, an attacker abused a flaw in Optimizely's account signup flow. That gave them a way to add their own code to some customer projects. Because the code was served from Optimizely's legitimate delivery network, browsers and most security policies simply trusted it.

Security researcher Scott Helme of Report URI found the malicious code in one hundred eighty-eight of roughly sixteen hundred Optimizely scripts he examined, belonging to one hundred seventy-eight organizations. Names in the reporting include Zoom, the BBC, CNN, Salesforce, GitLab, IKEA, HSBC, the crypto wallet maker Ledger and the airline KLM.

What did the code do? According to researchers, it watched for copied cryptocurrency wallet addresses and swapped in the attacker's address. It also tried to skim payment card numbers from checkout forms, and it reportedly loaded exploit code aimed at older iPhones and iPads.

Optimizely has confirmed the incident. It says the signup flaw is fixed and the malicious code has been removed from affected projects. Analysis by StepSecurity notes that cleanup was happening on the evening of November sixteen, so a clean file today does not prove it was clean on Sunday.

Why does this matter to you? Many companies treat marketing scripts as harmless. They are not. They run with full access to your pages, your forms and your customers' sessions. And a Content Security Policy that allows a vendor's domain will happily let that vendor's compromised code through.

So here is the to do list. If your sites use Optimizely Web, have your web team review the custom code in every project, rotate Optimizely credentials and tokens, and check what was served on Sunday. If you run checkout pages, talk to your payment provider about possible skimming exposure. And more broadly, take inventory of every third-party script on pages that handle logins or payments. Fewer scripts, tighter policies, and integrity checks where possible.

The second supply chain story is aimed squarely at developers building AI agents. Agent Framework is Microsoft's open source toolkit for building AI agents, and its Python package lives on PyPI, the Python Package Index.

On Tuesday evening, November seventeen, someone published two malicious versions of that package, about half an hour apart. According to Aikido and Wiz, both versions planted a small startup file that Python runs automatically every time the interpreter starts. The package does not even need to be imported. That file collected credentials for Azure, Azure DevOps and GitHub Actions and sent them to the attacker.

The clever part is that the malicious release still pulled in the genuine framework underneath. So applications kept working normally, and nothing looked broken. That is exactly what makes this kind of attack hard to spot.

Both bad releases have been removed from PyPI. Researchers note that after the first one was pulled, a second malicious version appeared, which suggests the attacker still had publishing access at that point. How they got it is not yet confirmed, and there is no official root cause from Microsoft so far.

Who is affected? Anyone who installed or rebuilt an environment since Tuesday evening with a loose version rule for this package. That includes build servers, CI runners and container images, not just developer laptops.

What to do today. Ask your engineering teams to search lockfiles, CI caches and recently built images for the affected releases of agent-framework. Pin to the last good version, which researchers identify as one point twenty-six point zero. And if you find a hit, treat it as a full credential compromise. Rotate every secret that machine could see, review cloud sign-ins, and check for new tokens or app registrations.

The bigger lesson is familiar but worth repeating. Pin your dependencies, use lockfiles, and give build pipelines the narrowest credentials possible.

A shorter one on endpoint security. Apple is tightening how Mac apps get access to your data, and it says AI agents are the reason.
